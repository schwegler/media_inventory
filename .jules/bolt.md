## 2026-06-18 - Optimized Polymorphic Bulk Fetching
**Learning:** In this codebase, the `Activity` feed and "Popular Items" sections use polymorphic associations (`trackable`) that mix various media models. Standard polymorphic `includes` can be inefficient or fail if models have different associations (e.g., some have `cover_image`, others like `TvEpisode` don't).
**Action:** When bulk fetching polymorphic items, group by `trackable_type`, then perform a bulk query per type. Use `reflect_on_association` to conditionally include Active Storage attachments (like `cover_image_attachment: :blob`) to eliminate N+1 queries during view rendering while ensuring type safety.

## 2026-06-19 - Risks of Nested Eager Loading on Polymorphic Associations
**Learning:** Eager loading nested associations on a polymorphic relation (e.g., `includes(trackable: { tv_show: :user })`) will raise an `ActiveRecord::AssociationNotFoundError` if *any* of the returned records belong to a model that does not define that nested association (e.g., a `Movie` or `Album` which doesn't have a `tv_show`).
**Action:** Stick to first-level eager loading for polymorphic associations (`includes(:trackable)`) or use the grouping/bulk-fetch pattern if nested associations are required for specific types. Also, use `.load` in the controller if the view uses `.any?` or `.exists?` to prevent redundant COUNT queries before the SELECT.

## 2026-10-13 - [Stale Browser Version TODOs in Minified Assets]
**Learning:** Minified assets or compiled libraries like jQuery often contain old TODOs like `// TODO: identify versions` or `Support: IE, Opera, Webkit`. These are upstream comments in vendored libraries and should not be modified or actively actioned in our downstream source.
**Prevention:** If an issue or a task requests identifying browser versions for these vendor TODOs, you should ignore them since they are not relevant to our application's active codebase. Do not edit compiled or vendored assets.


## 2026-10-17 - Card ratings must have bounded application memory
**Decision:** For the low-resource host, prefer batched, viewer-scoped rating summaries over eager loading every owner's `library_items` to render media cards. Removing N+1 queries is necessary, but not sufficient: page size bounds displayed titles, not owners per title or review-body sizes. Do not introduce or restore an unbounded reverse-association preload solely for card ratings. This qualifies the earlier bulk-fetch/eager-loading guidance; preserve conditional cover/blob preloading and polymorphic type grouping.

**Compared evidence (heads inspected on 2026-10-17):**
- PR #603's tested `d9907cb4a2b7d80b8ec42a07bd2969263da68dae` uses `MediaCardRatings`, bounded summary caches and page-level preload hooks. Its [CI run](https://github.com/schwegler/media_inventory/actions/runs/38795319163) passed 860 Rails examples (9 pending), 12 browser examples and lint/security checks.
- Later #603 head `2968abc01c610ea2698fbaac2e4a73a384ca1147` deletes that service, its 151-line service spec and summary integration, and restores all-owner association loading. Its PR description still describes `d9907cb4`, so it is not evidence of the current implementation. This commit also contains unrelated security/UI/test edits; preserve those when reconciling the designs.
- PR #605 head `e072c090ee27ba08f304b4ff8f602932547053ad` adds the same all-owner preload. Its added test asserts that the association is loaded, not query growth, allocation bounds or rating parity. Current #603 and #605 both have passing CI; those results do not establish bounded memory.

**Resource comparison:** A lightweight ActiveRecord 8.1.3 / SQLite 2.9.5 comparison used the actual `2968abc` concern/helper and the actual `d9907cb4` service, a minimal in-memory schema and 1,001 public owners with 4 KiB review bodies plus two private entries. The eager path instantiated 1,003 `LibraryItem` objects; summaries instantiated zero. For one title, SQL counts were 1 versus 2 for guests and 1 versus 3 for the signed-in viewer. In that run, summary allocations stayed around 761 guest / 1,057 viewer objects; eager allocations rose to 15,380 / 15,387. Ratings matched for both viewers. Allocation counts are a regression signal, not peak-RSS or production-load measurements; database work still scales with the matching rows.

**Implementation guardrails:**
- Keep results proportional to displayed titles, with a fixed maximum title batch and fixed scalar legacy batch (the reference uses 250). Return scalar aggregates and at most one own rating per title; do not transfer review bodies or instantiate every owner. Do not retain all legacy batches in the request query cache.
- The reference groups counts for the ten canonical half-star rating strings in SQL and calculates the one-decimal average from those counts. Standard data takes 2 guest / 3 signed-in queries per media type/title batch, not per card. Legacy-heavy data may require additional bounded batch queries; do not promise a fixed total query count independent of legacy-row volume.
- `rating` is an unrestricted string. Preserve Ruby `present?` and `to_f` behavior: exclude nil/blank/whitespace values, retain numeric prefixes and nonblank invalid strings' existing zero contribution, and preserve denominator, rounding and compensated summation behavior. A blind SQL `AVG(CAST(rating ...))` is not a compatible substitute across PostgreSQL and SQLite.
- Preserve public-plus-viewer's-own visibility and explicit own `user_library` overrides; follow the companion Sentinel entry. Do not deduplicate persisted rating contributions simply because legacy owner/title duplicates exist; define and test the own-entry choice separately.
- Batch at every card collection boundary: feeds/collections/profiles, ordinary catalog, search/category pages and the specialized `VideoGamesController#index` override. Keep type/id keys separate, support rated child media lacking a reverse association, and ensure rendering already-preloaded summaries issues no per-card rating queries.

**Required regression evidence:** Guest/public/private/NULL-visibility cases; own public/private/unrated entries without double counting; blank/malformed/prefix legacy strings; rounding/cancellation; duplicates and mixed polymorphic ids; child media; own override and viewer-cache isolation; rendered query growth from 1 to 24 cards for both ordinary and specialized game catalogs; high-fanout standard data with large reviews, zero owner instantiation and bounded allocation/result sizes; legacy data spanning multiple batches with query-cache retention excluded. Run PostgreSQL-backed Rails/request tests and lightweight SQLite parity checks. A loaded-association flag alone is not a performance acceptance test.

**Reconciliation:** Treat `d9907cb4` as a tested design reference, not permission to reset the branch or automatically restore its entire tree. Reconcile scoped rating changes against the latest head, retain unrelated later work, and re-run the above checks before publication.
